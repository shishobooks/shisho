# Public demo scale-to-zero hosting

_Research current as of 2026-07-31. Primary sources only._

## Answer

Use **Google Cloud Run** as the planning default for the Public Demo, with two explicit validation gates before deployment:

1. prove that EPUB, CBZ, PDF, and M4B range reads perform acceptably through a read-only Cloud Storage FUSE mount; and
2. confirm in a billing test that Cloud Run's new spend cap covers the network-egress SKUs generated by this path.

The proposed shape is:

- deploy the unchanged, version-pinned Shisho release image with request-based billing, `min-instances=0`, `max-instances=1`, and a 60-minute request timeout;
- mirror the release image into a same-region Artifact Registry repository rather than building a demo image;
- keep the prepared corpus and SQLite database in a private, single-region Cloud Storage bucket mounted read-only;
- copy only the SQLite database into Cloud Run's writable in-memory filesystem before starting Shisho, while serving media from the read-only mount;
- use Cloud Run's direct domain mapping for `demo.shishobooks.com`; and
- set a Cloud Run spend cap below the desired ceiling, for example $8 for a roughly $10 ceiling, plus an alerts-only whole-project budget for storage and registry costs.

Cloud Run is the only candidate found that combines a standard container, native scale to zero, a read-only object-storage filesystem mount, requests as long as 60 minutes, and a service-level spend cap. Its important compromise is that direct custom-domain mapping is still Preview and explicitly not recommended for production. That is acceptable only because the Public Demo permits best-effort uptime. Google's recommended external Application Load Balancer is not economical here: its first forwarding rule is $0.025/hour, about $18.25 in a 730-hour month, before data processing and egress charges ([Cloud Run domain mapping](https://docs.cloud.google.com/run/docs/mapping-custom-domains), [load-balancer pricing](https://cloud.google.com/load-balancing/pricing)).

## Recommended candidate: Google Cloud Run

### Container, scaling, startup, and media

Cloud Run accepts Linux x86-64 OCI/Docker images, allows a configured container port, and scales a revision to zero by default when it has no traffic. A service must listen within four minutes. Its writable filesystem is in memory and disappears with the instance, which is suitable for a disposable copy of SQLite but means the database size counts against RAM ([runtime contract](https://docs.cloud.google.com/run/docs/container-contract), [autoscaling](https://docs.cloud.google.com/run/docs/about-instance-autoscaling)). Cloud Run permits container entrypoint and argument overrides, so corpus preparation can be deployment configuration rather than a derived demo image ([container configuration](https://docs.cloud.google.com/run/docs/configuring/services/containers)).

A Cloud Storage bucket can be mounted read-only and exposed as ordinary paths. Reads can request only portions of an object, which is important for media range requests. The mount uses container memory for caches and per-open-file buffers. Cloud Storage FUSE is not fully POSIX-compliant and provides no file locking for concurrent writes, so the prepared SQLite database should **not** run directly from the mount; copy it to ephemeral writable storage first ([Cloud Storage volume mounts](https://docs.cloud.google.com/run/docs/configuring/services/cloud-storage-volume-mounts)).

Cloud Run's default request timeout is five minutes and can be raised to 60 minutes. Set it to 60 minutes for long M4B/PDF responses, while retaining normal HTTP range behavior in Shisho ([request timeout](https://docs.cloud.google.com/run/docs/configuring/request-timeout)).

Set `max-instances=1`. This protects the single disposable SQLite copy from divergent replicas and limits simultaneous compute allocation. Google documents that a maximum is not an absolute instantaneous ceiling during deployments, maintenance, or spikes, so it is a cost control but not a hard billing cap ([maximum-instance behavior](https://docs.cloud.google.com/run/docs/about-instance-autoscaling#about_maximum_instances_for_services)).

### Domain and TLS

Direct Cloud Run domain mapping supports subdomains, automatically issues and renews a Google-managed certificate, and is available in `us-central1`, `us-east1`, and other listed regions. It is also Preview, has documented latency issues, and is not recommended for production. Certificate provisioning can take up to 24 hours ([domain mapping](https://docs.cloud.google.com/run/docs/mapping-custom-domains#run)). For this best-effort demo, map `demo.shishobooks.com` directly in `us-central1`; do not add the fixed-cost load balancer unless the map later raises the monthly target.

### Cost model

Use request-based billing and zero minimum instances. Cloud Run bills startup, shutdown, and time with at least one request in progress. The monthly free grant is 180,000 vCPU-seconds, 360,000 GiB-seconds, and 2 million requests. Above it, Tier 1 request-based rates are $0.000024 per active vCPU-second, $0.0000025 per active GiB-second, and $0.40 per million requests. Long-lived media responses consume active CPU/RAM billing time even if the application is mostly waiting on the client, while concurrent requests on one instance share the allocation ([Cloud Run pricing](https://cloud.google.com/run/pricing)).

Public egress is likely the dominant ordinary cost. Cloud Run includes 1 GiB/month of North American outbound transfer and then uses Premium Network Service Tier pricing. The first paid North American tier is $0.12/GiB, so 30 paid GiB is about $3.60 and 40 paid GiB is about $4.80 before compute overages ([Cloud Run pricing](https://cloud.google.com/run/pricing), [VPC network pricing](https://cloud.google.com/vpc/network-pricing#internet_egress)). This makes the $0-$5 target plausible, not guaranteed; actual media bytes and response duration must be observed.

For the corpus, Cloud Storage Standard in `us-central1` includes 5 GB-month, 5,000 Class A operations, and 50,000 Class B operations in its Always Free allowance. Above that, single-region Standard storage in Iowa is $0.000027397/GiB-hour, about $0.02/GiB-month; same-location transfer from Cloud Storage to Cloud Run is free ([Cloud Storage pricing](https://cloud.google.com/storage/pricing#cloud-storage-always-free), [same-location transfer](https://cloud.google.com/storage/pricing#network-buckets)).

No image build is required. Artifact Registry includes 0.5 GiB-month, then charges $0.000136986/GiB-hour, about $0.10/GiB-month; transfer to Cloud Run in the same location is free. Mirror each promoted Shisho release digest and delete superseded mirrors as needed ([Artifact Registry pricing](https://cloud.google.com/artifact-registry/pricing)).

### Spending safeguard

Google Cloud spend cap budgets now list Cloud Run as an eligible service. A cap is scoped to one project and one service. At 100% of the gross estimated target, Google pauses new usage for that service until the cap is manually lifted. Enforcement is not instantaneous, in-flight work completes, and overage caused by reporting latency is still billed. Google therefore advises setting the cap below the absolute limit ([spend cap budgets](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps)).

Set the Cloud Run cap to about $8, not $10. Also configure an alerts-only project budget because a Cloud Run cap does not pause persistent storage/registry charges and cannot cover several services in one cap. **Fog:** the spend-cap documentation names Cloud Run but does not say whether Premium Tier internet egress billed for a Cloud Run response is included in that service's estimated spend. Verify this with generated media traffic and the billing SKU/service attribution before treating the cap as the required safeguard.

## Viable alternatives

### Scaleway Serverless Containers

Scaleway accepts any HTTP container from a public registry, supports command/argument overrides, scales to zero after 15 idle minutes when `min-scale=0`, permits `max-scale=1`, supports requests from 10 seconds to 60 minutes, and supports custom domains with automatically renewed Let's Encrypt certificates ([concepts](https://www.scaleway.com/en/docs/serverless-containers/concepts/), [limits](https://www.scaleway.com/en/docs/serverless-containers/reference-content/containers-limitations/), [custom domains](https://www.scaleway.com/en/docs/serverless-containers/how-to/add-a-custom-domain-to-a-container/), [TLS FAQ](https://www.scaleway.com/en/docs/serverless-containers/faq/#can-i-use-my-own-tls-certificates-for-custom-domains)).

It has no block-storage attachment. Ephemeral disk is free and can be as large as 24,000 MiB, but its permitted size is tied to allocated memory and Scaleway does not publish the mapping. The practical shape is therefore a private, versioned Object Storage archive downloaded before binding the service port; every new instance repeats that download. The archive remains separate from the application image, but cold-start time and low-tier disk capacity require a prototype ([storage and block-storage FAQ](https://www.scaleway.com/en/docs/serverless-containers/faq/#how-can-i-store-data-in-my-serverless-resource), [ephemeral storage](https://www.scaleway.com/en/docs/serverless-containers/concepts/#ephemeral-storage)).

The monthly free tier is 400,000 GB-seconds of RAM and 200,000 vCPU-seconds; overage is €0.000002/GB-second and €0.00001/vCPU-second. Ephemeral storage and container ingress/egress are free ([serverless pricing](https://www.scaleway.com/en/pricing/serverless/), [billing FAQ](https://www.scaleway.com/en/docs/serverless-containers/faq/#how-am-i-billed-for-serverless-containers)). Object Storage Standard Multi-AZ is €0.01606/GB-month, requests and ingress are included, and the first 75 GB/month of egress is free; same-region transfer is free ([storage pricing](https://www.scaleway.com/en/pricing/storage/)). A public Scaleway registry mirror is free up to 75 GB with free transfer, although an external public registry is also supported ([registry pricing](https://www.scaleway.com/en/docs/container-registry/faq/#how-am-i-billed-for-scaleway-container-registry), [deployment sources](https://www.scaleway.com/en/docs/serverless-containers/how-to/deploy-container/)).

Scaleway offers estimated billing alerts through email, SMS, or webhook, but the documentation describes notification only, not service suspension or a hard cap ([billing alerts](https://www.scaleway.com/en/docs/billing/how-to/use-billing-alerts/)). It becomes the best fallback only if a prototype shows that a resource allocation with a worst-case one-instance monthly cost near $10 can hold and serve the complete corpus.

### Azure Container Apps, Consumption plan

Azure Container Apps accepts public/private Linux x86-64 images and supports init containers. An init container can download the prepared archive before Shisho starts, or the standard image's command can be overridden to do the same ([containers](https://learn.microsoft.com/en-us/azure/container-apps/containers)). An `EmptyDir` can be shared between init and app containers, persists only for the replica lifetime, and provides 1, 2, 4, or 8 GiB according to replica CPU allocation. Azure Blob Storage cannot be mounted directly; Azure Files can, but that introduces separately billed permanent storage and is unnecessary for this immutable design ([storage mounts](https://learn.microsoft.com/en-us/azure/container-apps/storage-mounts)).

HTTP scaling permits `minReplicas=0` and `maxReplicas=1`. External ingress provides TLS termination, HTTP/1.1 and HTTP/2, and a fixed 240-second request timeout. `demo.shishobooks.com` can use a CNAME and a free automatically renewed managed certificate ([scaling](https://learn.microsoft.com/en-us/azure/container-apps/scale-app), [ingress](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview), [managed certificates](https://learn.microsoft.com/en-us/azure/container-apps/custom-domains-managed-certificates)). The four-minute timeout is a meaningful risk for full-file audio responses; range requests must complete inside it.

The Consumption plan has no charge at zero replicas. Per subscription per month it includes 180,000 vCPU-seconds, 360,000 GiB-seconds, and 2 million requests; requests, active CPU, and active RAM are separate meters above those grants ([billing](https://learn.microsoft.com/en-us/azure/container-apps/billing), [pricing](https://azure.microsoft.com/en-us/pricing/details/container-apps/)). Azure also includes the first 100 GB/month of internet egress in North America and Europe ([bandwidth pricing](https://azure.microsoft.com/en-us/pricing/details/bandwidth/)). Blob Storage separately charges capacity, operations, and transfer ([Blob cost model](https://learn.microsoft.com/en-us/azure/storage/common/storage-plan-manage-costs)). Azure Container Apps can pull from a public registry, so Azure Container Registry is optional and its daily base charge should be avoided ([container registries](https://learn.microsoft.com/en-us/azure/container-apps/containers#container-registries)).

Azure budgets notify but do not affect resources or stop consumption, and cost data is typically delayed 8-24 hours. Azure's spending limit is unavailable for pay-as-you-go subscriptions and cannot be set to a custom amount ([budgets](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets), [spending limits](https://learn.microsoft.com/en-us/azure/cost-management-billing/manage/spending-limit)). A budget-triggered automation could disable the app, but that delay is not a safeguard around $10. This keeps Azure viable but behind Cloud Run and Scaleway.

### Render Free web service

Render Free web services can run a prebuilt image, allow a custom Docker command, include custom domains and managed TLS, and spin down after 15 idle minutes. A cold wake takes about one minute. The filesystem is ephemeral and is lost on spin-down, so a startup command must download the prepared corpus each time ([Docker deployment](https://render.com/docs/docker), [free services](https://render.com/docs/free), [custom domains](https://render.com/docs/custom-domains)).

A workspace receives 750 free instance-hours. If free hours are exhausted, Render suspends free services until the next month. Bandwidth above the included amount is billed when a payment method exists; without one, free services are suspended for the remainder of the month instead. That no-card behavior is the strongest simple safeguard among the fallbacks ([free-service limits](https://render.com/docs/free#free-web-services)).

The concerns are substantial: Render says free instances are not for production, may restart them at any time, and does not document available runtime filesystem capacity on the cited pages. A media demo can also consume the included outbound allowance quickly. Use this option only if a no-payment-method account is operationally acceptable and an end-to-end corpus/download/playback prototype passes.

## Eliminated and borderline options

- **AWS App Runner:** not scale to zero. It always maintains at least the configured minimum provisioned instances and bills their memory. At $0.007/GB-hour, one 1 GB provisioned instance costs about $5.11 in a 730-hour month before active CPU, storage, logs, or egress ([autoscaling](https://docs.aws.amazon.com/apprunner/latest/dg/manage-autoscaling.html), [pricing](https://aws.amazon.com/apprunner/pricing/)).
- **AWS Lambda container images:** not the standard Shisho container. A Lambda image must implement the Lambda Runtime API through a runtime interface client and run with a read-only root filesystem, requiring a Lambda-specific image or adapter ([Lambda image requirements](https://docs.aws.amazon.com/lambda/latest/dg/images-create.html#images-reqs)).
- **Fly.io Machines:** technically scales to zero and can use a custom domain, but stopped Machines still bill rootfs at $0.15/GB-month, public egress is metered, every organization needs a credit card, and Fly explicitly provides no billing alerts or soft ceiling. This fails the requested safeguard even though a single small Machine can be cheap ([autostop](https://fly.io/docs/launch/autostop-autostart/), [pricing](https://fly.io/docs/about/pricing/), [cost management](https://fly.io/docs/about/cost-management/)).
- **Koyeb Free:** borderline, not recommendation-ready. It scales to zero and includes one 0.1 vCPU, 512 MB, 2 GB SSD instance, but the free instance cannot attach volumes or customize scaling. The 2 GB local ceiling must contain the unpacked database and all media, and Koyeb's broader scale-to-zero feature remains Preview ([instances](https://www.koyeb.com/docs/reference/instances#free-instances), [scale to zero](https://www.koyeb.com/docs/run-and-scale/scale-to-zero), [volumes](https://www.koyeb.com/docs/reference/volumes)). It can be reconsidered only if the final corpus is proven below that ceiling and an account-level spending safeguard is documented.

## Questions and fog for the map

1. Does a Cloud Run spend cap include the Premium Tier internet-egress SKUs produced by Cloud Run media responses, or only request/CPU/RAM SKUs?
2. Do Shisho's browser readers and audio player consistently issue bounded range requests, and how do those reads behave through Cloud Storage FUSE under one instance?
3. What are the compressed and unpacked sizes of the final prepared corpus and SQLite database? That decides whether Scaleway, Azure, Render, or Koyeb can use ephemeral-download startup at a low resource tier.
4. Is Preview direct domain mapping acceptable for the Public Demo, given that the supported Google load-balancer path alone exceeds the monthly target?
5. What active CPU/RAM hours and egress result from a small realistic traffic replay? The free tiers make request count a weak predictor; media duration and bytes dominate.
