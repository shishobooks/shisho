# The Shisho App

The Shisho app for iPhone and iPad (`ios/`), and one suite of Maestro flows (`harness/flows/`) that the Android app will run unchanged. Each platform is written natively with no shared code (ADR 0021); `android/` holds only the generated API types and their decode tests until the Android app joins it. The decisions are in ADRs 0020 to 0026; the server side is in `docs/agents/backend/change-feed.md`.

## Rules every change needs

- **A screen with `.searchable` on a tab's own stack binds the search's `isPresented` to `model.searchActive(on:)` and opens pages with `model.push`, never `NavigationLink(value:)`.** A sheet with its own stack, such as the filters' pickers, keeps its own state. On iOS 26 a stack with a page over an active search can't be emptied, and `TabNavigation` closes the search on every push and pop.
- **Every screen reads the account's own SQLite database; the network only updates it.** A screen never shows a server response directly, so everything shown works offline. Each account has its own database under its folder, owned by native code. On iOS it's GRDB: screens observe it with `observing(...)` (`ios/Shisho/UI/Observed.swift`) rather than refetching after a sync.
- **A change the user makes goes into the account's journal, never straight to the server** (ADR 0024): write it through `CatalogStore` (`ios/Shisho/Core/CatalogStore+Listening.swift`) and the sync sends it. Record it where the work happens, such as `AudioPlayer` or `ReadingTracker`, never in a view, so it's kept with the screen closed, the phone locked, or from CarPlay. A new kind of change is a new event type in `pkg/shishoapp/types.go`, sent only to servers that list its capability.
- **Anything kept per account is named in `AccountData`** (`ios/Shisho/Core/AccountStore.swift`): a new per-account settings key, folder, or cache goes there, so removing the account, as signing in to a server set up again does, removes it too.
- **A schema change is a new GRDB migration**, appended to `CatalogStore.migrator`. Never edit one that has shipped: devices that already ran it won't run it again. An unreleased one is edited in place; debug builds rebuild a database whose migrations changed.
- **Swift 6 language mode, so data races are compile errors.** Make code provably safe (value types, `let`s of `Sendable` types, actors, `@MainActor`) rather than reaching for an escape hatch; `mise lint:swiftconcurrency` rejects one without a reason.
- **Never write an API type by hand.** They're generated from the Go structs by `mise tygo` (`tools/apptypes`) into gitignored folders: Swift in `ios/ShishoAPI/Sources/ShishoAPI/Generated/`, in namespaces named for the Go packages (`Shishoapp.FeedBook`), and Kotlin in `android/api/src/main/kotlin/generated/`, one package per Go package. Change the Go struct and run `mise tygo`.
- **A feature that needs anything new from the server is behind a capability** (ADR 0020). That covers a new route, event type, request field, or kind of record. A new meaning for something that exists arrives the same way, as a new field or route, because the server keeps the old meaning working for every app protocol it accepts. The server lists the capability in `pkg/shishoapp/contract.go` in the same change, and the app turns the feature on only for a server that lists it and hides it elsewhere, so an App Store copy keeps working against an older server. The protocol 1 baseline is what the first release with the app ships; after that it never changes. Until the first release with the app, what's new from the server joins the protocol 1 baseline instead of getting a capability. After it, a capability that isn't in a release yet can still be renamed or reshaped, as an unreleased migration can be edited, since no released app or server depends on it.
- **Decode leniently and keep data on refusals** (ADR 0020). Unknown kinds and fields are skipped, an unknown enum value is its own case, and a 426 or an unreachable server leaves everything on the device working.
- **One HTTP layer per account carries every request** (`ios/Shisho/Core/APIClient.swift`). It skips the URL cache, so capability headers are only read from live responses. Downloads' background session comes from it too (`backgroundSession`, `downloadRequest`).
- **Anything that opens a File's bytes uses its Download first** (`DownloadManager.localFile`), and only then streams it or downloads it with `DownloadManager.fetchNow`, as `AudioPlayer` and `ReaderModel` do, never into a cache of its own; a File read to its end calls `DownloadManager.finished` so Remove when finished applies.
- **Ask the account's `ServerReachability` (`client.reachability`) before reaching the server**, and say at once that something needs a connection rather than trying: `APIClient` requests already fail fast while it says no, but the system player and anything else making its own requests must check it, as `AudioPlayer` does, and react to `AppModel.connection` changing. Background Download transfers are the exception: iOS runs and retries them itself, with the app suspended, whatever the app last heard.
- **Every control has an accessibility identifier and a VoiceOver label.** Flows find controls by identifier or visible text, never by position, so the Android app can run them unchanged: give the same control the same identifier on both platforms.
- **Strings go in the String Catalog** (`ios/Shisho/Resources/Localizable.xcstrings`). Command-line builds don't update it; run `mise ios:strings` after adding or removing strings.
- **The look comes from the web app**: its colors, from `app/index.css`, are in the asset catalog, and its typefaces, Geist and Geist Mono, are bundled. Use `Theme`, `Font.geist`, and `Font.geistMono`, never system colors or system fonts for brand surfaces. Icons are the web's Lucide set, through `Icon` and `Lucide` (`ios/Shisho/UI/Icons.swift`); `mise lint:icons` rejects SF Symbols. CJK text falls back to iOS's own fonts, such as Hiragino for Japanese, on purpose: bundling Noto Sans CJK would add megabytes and needs a font cascade that SwiftUI's `.custom` can't express.

## Accessibility

Each screen has to work with VoiceOver, at accessibility text sizes, and on iPad. These are the traps agents have hit:

- **VoiceOver doesn't run in the Simulator.** Check what it would read in the accessibility tree (the device tools' `snapshot`). For a wider sweep, run Apple's `performAccessibilityAudit` from a throwaway UI-test target. Its contrast findings flag ordinary dark-on-light Geist text, so judge them against the web's colors instead of fixing each one. Say what you couldn't hear, so the user tries it on a phone.
- **A screen hidden with opacity is still read.** VoiceOver reaches into hidden screens kept alive that way, even with `accessibilityHidden`, once they hold a `NavigationStack`. Keep tabs alive in a `TabView` with its bar hidden, as `MainTabs` does.
- **Don't wrap a `Button` in a combined or ignored accessibility element.** It becomes a button inside a button, which VoiceOver and the harness can't press reliably. Label the button itself and add `.isSelected` when it's on.
- **Fixed sizes clip at large text.** Size text with `Font.geist` relative to a text style, size row heights with `@ScaledMetric`, and use `minHeight` rather than `height`. Check new screens at `accessibility-extra-large` (the device tools' `settings text-size`), which breaks layouts that look fine at default size. Things meant to stay a fixed size, like the tab bar, cap their size and offer the Large Content Viewer.
- **Every gesture needs another way in.** Drag to reorder, swipe to dismiss, and sliders need `accessibilityActions` or `accessibilityAdjustableAction`.
- **Tap targets are at least 44 points**, even when the drawn control is smaller.
- **Text uppercased for looks is read letter by letter.** Give it an `accessibilityLabel` in normal case. Decorative chevrons and icons beside a label are `accessibilityHidden`, and a picker announces its current choice as its `accessibilityValue`.

## Building

The mise tasks are the way in: `mise tasks | grep -E '^(ios|android|mobile)'` lists them. The Xcode project is generated from `ios/project.yml` by XcodeGen and isn't committed; edit `project.yml`, never the project.

- **Command-line builds use `ios/build/`**, never Xcode's DerivedData, so a terminal build and Xcode, or two worktrees, never build or resolve packages in the same place. Pass `-derivedDataPath build/DerivedData` to any `xcodebuild` you run yourself.
- **Simulator builds sign ad hoc with the team** (`CODE_SIGN_STYLE=Manual CODE_SIGN_IDENTITY=-`), as the tasks do. An unsigned build (`CODE_SIGNING_ALLOWED=NO`) can't write the Keychain, so it signs in and then forgets the sign-in on relaunch.
- **Signing**: `ios/Config/Shisho.xcconfig` sets the maintainer's team and the bundle id. Debug builds are a separate app, Shisho Dev, whose bundle id adds `.dev` (`Debug.xcconfig`), so open that id when driving a debug build. Someone else copies `Signing.local.xcconfig.example` to the gitignored `Signing.local.xcconfig`.
- **QA against `mise start:qa`**, a throwaway server seeded with the harness's fixtures, never the dev database. It listens on the LAN too, so a phone can reach it.
- **The checks run on simulators of their own**, cloned by `tools/appharness` from a base it makes once: each worktree keeps one for `mise ios:test`, one for `mise ios:harness`, and one more for the second half of a parallel run (`tools/appharness/worktreesim.go`). Never boot or change the base, never QA on the worktree's own simulators (they're named `Shisho Worktree`, and the next run resets them), and don't run tests on a simulator you share with another worktree; use the mise tasks. `mise cleanup` deletes the worktree's simulators before the worktree goes.

## Checks

`mise mobile:check` runs them all; `mise check:quiet` leaves them out. While iterating:

- Generated types → `mise lint:apptypes`, then `mise ios:test` (decode tests on the host, app tests on a simulator) and `mise android:test`.
- App code → `mise ios:test`, which builds the app first.
- Anything a flow covers → `mise ios:harness`, which needs ffmpeg to make its fixtures when they aren't cached. `-- -keep` keeps the server log and Maestro's screenshots. `-- -parallel 2` splits the flows across simulators run at once, each with its own server, for running them all. A flow that changes the world around the app, such as taking the server offline, calls the harness's control endpoint (`tools/appharness/ios.go`).
- The too-old paths → start the server with `SHISHO_DEV_APP_PROTOCOLS` set to the range it should accept: a range above the app's protocol makes the app too old, and one below it makes the server too old for it.

## The signoff

Pull requests from this repository's own branches, other than Dependabot's, don't run the iOS unit tests or flows on GitHub's macOS runners, which take several times longer. `CI OK` waits instead for a commit status that `mise ios:signoff` posts from a Mac once every unit test and flow passes on the commit; `scripts/app-changes.sh` decides which pull requests need it: any that change something other than the web app, docs, and the few other paths it rules out.

- **Run it on the pull request's final commit, pushed, with nothing uncommitted.** A new commit, a merge from master included, needs its own.
- **Only `mise ios:signoff`, or the workflow the `ios-on-github` label runs, posts that status.** Never post it with `gh api` or touch the passes the signoff records: it tells the maintainer every unit test and flow passed on that commit.
- **When the checks fail on the Mac for a reason outside the change**, such as its audio output breaking, fix the Mac, not the flows. If that can't wait, the `ios-on-github` label runs the pull request's unit tests and flows on GitHub's runners instead, and again on every push until the label comes off. On a busy Mac, `-- -parallel 1` runs one shard at a time.

## Keeping runs fast

Agents run these checks many times a ticket, so a few seconds in every flow add up to minutes.

- **A new flow needs a time in `flowSeconds`** (`tools/appharness/shard.go`), which splits the flows into shards; `TestFlowSecondsNameEveryFlow` fails until it has one, and says how to pick it.
- **What's reused between runs**: the worktree's simulators, kept booted, each run removing the app and its Keychain first; and the harness's fixtures, cached under the user's cache folder and keyed by the files they're made from (`fixtureSources` in `tools/appharness/fixtures.go`), so neither needs clearing when something changes. `SHISHO_HARNESS_FRESH=1` reuses neither, for a run from a clean slate. CI clones a fresh simulator each run and caches the fixtures by the same key.
- **Sign in with `subflows/launch_signed_in.yaml`**, which signs a debug build in as it launches, not with the sign-in screen, which costs each flow around 20 seconds of typing. Only flows about the sign-in screen itself use `subflows/sign_in.yaml`. The shortcut is `#if DEBUG` (`HarnessSignIn`), so release builds don't have it.
- **Launch as the other flows do**: without `permissions: {}` Maestro grants the app every permission on each launch, which is slow on CI. `TestFlowLaunchesSkipPermissionsAndASecondStop` (`tools/appharness`) checks every flow's launches.
- **Move through the app's screens rather than relaunching it**, unless the flow checks what survives a relaunch: launches are slow on CI.
- **Listen only as long as what the flow checks needs.** Listening is real time: Reading Sessions and the periodic saves of the place are timed by the clock, not the place, so playing faster doesn't shorten a flow that checks them. A flow that needs a place reached, not time listened, skips to it.

## What earns a flow

Every flow runs in every signoff and in master's run on GitHub's runners, so each one adds its time to every app pull request, and the suite only grows. Write a Maestro flow only for what needs the whole system at once:

- **The app and the server together**: what the app sends reaching the server (the journal's changes, Reading Sessions, places), what the server changes reaching the app (an access change, a server set up again), and signing in.
- **What survives the app's own lifecycle**: a kill and relaunch, going offline and back, signing out with changes not yet sent.
- **iOS itself, where a unit test would have to fake it**: playing audio, importing from Files.

Everything else goes in the app's unit tests (`ShishoTests`, run by `mise ios:test`): what a screen shows for a given state, settings and their limits, the rules behind a control (what Previous does partway into a chapter, how a sleep timer counts down), and parsing and layout math. Put the rule in a type the test can call, not in the view, as `ReaderSettings`, `ListeningRules` and `SleepTimerRules` do. A unit test has to be written again in Kotlin for Android, while a flow runs on both, but that's still far cheaper than a flow every pull request pays for.

Before adding a flow:

- **Extend a flow that already gets there.** A check on a screen an existing flow already reaches costs seconds; a new flow costs a launch, a sign-in and the walk to that screen.
- **A ticket's QA checklist is not a list of flows.** It's checked by hand once. Only what a later change could break without anyone noticing, and a unit test can't reach, needs a flow.
- **Delete a flow its unit tests replace**, in the same change.

## Writing flows

GitHub's runners still run the flows after every merge to master, and for pull requests from forks and Dependabot. Their macOS simulators stall now and then: a view hierarchy read or the app's main thread can freeze for around 10 seconds, so a flow that passes locally can still fail there. The signoff runs on a fast Mac that rarely stalls, so a passing signoff doesn't show a flow is safe on GitHub's runners: follow these rules even when the signoff passes. Before merging a new or changed flow, add the `ios-on-github` label once to run it on GitHub's runners, then take the label off. Otherwise master's run after the merge is the first place a stall shows; treat a flow that fails there as a flake to fix, not a run to repeat. When a flow fails on CI, read the timestamps in the Maestro logs of the failed job's `harness-output` artifact before treating the failure as an app bug. Write flows to tolerate those stalls:

- **Never assert a state that lasts only a few seconds**, such as a short chapter or a narrow window of the playback position. Assert a state that stays put (the last chapter once playback stops), or an open-ended one ("at least 0:12", not "0:12 to 0:19"). To listen for a while from a place that varies, build the pattern from that place, as `scripts/note_listen_target.js` does, and start from a known place (`subflows/rewind_harbor_lights.yaml`) when the listen could otherwise run into the next chapter.
- **Wait for the UI with `extendedWaitUntil` and a timeout of at least 30 seconds.** A longer timeout costs nothing when the flow passes, and a 10 to 15 second one fails on a single stall.
- **Signing in can take most of a minute on CI**, where the server can wait that long for CPU. Both sign-in subflows wait until the app is signed in, so a flow's own waits start from a signed-in app.
- **Check the server with a script that polls it**, then an `assertTrue` on the verdict the script recorded in `output.serverCheck`, as the `assert_*.js` scripts do: each retries its check, waiting between tries on the harness's control endpoint (Maestro's scripts have no sleep), until it passes or its deadline, set to outlast a stall, passes. A check that can't change while it polls, such as what the app showed, runs once first. Never check after a fixed wait, which costs its whole length when the sync lands at once and fails when a stall outlasts it. Not in a `retry` either: Maestro caps it at three retries, and it only retries Maestro's own failures, so a script that throws fails the flow on its first try.
- **A stall can drop a tap.** When a later step needs the tap's result, such as a screen it opens or a state it toggles, repeat the tap until the result shows, checking the state before each retry so a late first tap and a retry can't undo each other, as `subflows/pause_player.yaml` does. Use `repeat` with `while`, not `retry`, which taps again without checking whether the first tap landed. A tap that's safe to repeat, such as one opening a sheet, can instead take `retryTapIfNoChange: true`, which taps again when the screen doesn't change; Maestro doesn't by default.
- **A stall can drop typed text, even a whole field.** Wait for what the typing should produce, such as a search result, and when it doesn't come, clear the field and type it again, a bounded number of times. Sign-in screens go through `subflows/finish_sign_in.yaml`, which types every field again when the screen is still there.
- **Tap a screen that keeps changing**, such as a playing player, through `subflows/tap_player.yaml`. A plain `tapOn` waits for the screen to settle, and while the position ticks it waits out its whole timeout, which can be longer than the state being checked lasts.
- **`centerElement` on something that can't reach the middle**, such as a title in the last row, keeps swiping before Maestro settles for it being visible. Give that `scrollUntilVisible` a generous timeout.

CI's runners can also have an older iOS, and an Xcode with a different Swift, than this Mac: the harness uses the newest iOS runtime installed, and the runner image's can lag a release behind (in `setup-ios`, the simulator cache key lists the image's runtimes). To run the flows on that iOS, install its runtime and create an iPhone simulator on it. Boot it once, shut it down, and apply what `disallowPasswordAutoFill` (`tools/appharness/simulator.go`) sets, or iOS's Save Password prompt covers the tab bar after each sign-in. Then run `SHISHO_SIMULATOR_BASE=<its UDID> mise ios:harness`, and delete the simulator afterwards. On iOS 26, a crash on the `com.apple.SwiftUI.AsyncRenderer` thread in `_dispatch_assert_queue_fail`, with `ForEachState.item(at:offset:)` under the app's closure, is a `ViewThatFits` measuring a `ForEach` during an animation frame off the main thread, where Swift 6's isolation check traps. A fixed set of rows can be written out instead, as `PreciseStars` does.
